# NEAR Auth (FastAuth) для «Save progress with Google»

Дата: 2026-11-11. Метод: npm registry, tarball-и пакетів (читав, не запускав), вихідний код `Peersyst/fast-auth` (гілка `main`), docs.auth.near.org і docs.near.org, живі запити до Auth0-тенанта і testnet RPC.

## Вердикт

**Технічно можливо, але не за 2-3 години і не на нашому домені.**

1. **Блокер:** спільний dev `clientId` на testnet пускає лише два callback-и: `http://localhost:3000` і `https://example.fast-auth.com`. Будь-який інший origin (наш домен, `localhost:5173`, `127.0.0.1:3000`) Auth0 відхиляє з `403 Callback URL mismatch`. Отже судді на нашому домені вхід через Google не пройдуть, поки Peersyst не додасть наш origin у спільний клієнт. Форма заявки (https://form.typeform.com/to/VWHjf3HV) описана як заявка на mainnet, і скільки чекати відповіді, невідомо.
2. **Гостьовий акаунт не прив'язати до Google напряму.** `p-<16hex>.brinewar.testnet` створює контракт лише з function-call ключем, повного ключа немає ні в кого. Отже додати на цей акаунт MPC-ключ Google не може ніхто. Прогрес доведеться переносити в контракті на новий акаунт, яким керує Google.
3. **Потрібен власний relayer з повним ключем.** `fast-auth.testnet::sign` є `#[payable]`, і без 1 yocto MPC падає (див. «Відомі проблеми»). Function-call ключ депозит не прикріпить, а публічного relayer-а немає. Сервер зараз має повний ключ лише від `brinewar.testnet` (deployer).
4. Реалістична оцінка для варіанту нижче: **4-5 годин** разом з тестами контракту, сервером, фронтом і e2e на `localhost:3000`. Окремо треба рішення тімейта щодо relayer-ключа.

Рекомендація: сьогодні ж попросити NEAR Auth / Peersyst додати наш origin у тестовий клієнт. Якщо до кінця дня 2 відповіді немає, показати соцвхід лише у відео з `http://localhost:3000`, а в README чесно написати, що на домені він вимкнений через whitelisting.

## 2. API (з вихідного коду 1.4.2 / 1.4.1)

### Ініціалізація на testnet

```ts
import { FastAuthClient } from "@fast-auth-near/browser-sdk";
import { JavascriptProvider } from "@fast-auth-near/javascript-provider";

const provider = new JavascriptProvider({ network: "testnet", clientId: "np8paqIpMWmNbzT4xAvOOapZBjsOpptl" });
const client = new FastAuthClient(provider, connection, {
  fastAuthContractId: "fast-auth.testnet",
  mpcContractId: "v1.signer-prod.testnet",
});
```

`FAST_AUTH_AUTH0_DEFAULTS.testnet = { domain: "login.testnet.fast-auth.com", audience: "https://api.testnet.fast-auth.com", signingAudience: "auth0.jwt.fast-auth.testnet" }`. Значення `clientId` і адреси контрактів взято зі сторінки https://docs.auth.near.org/resources/testnet і з `examples/spa/config.json`.

`connection` очікується як `Connection` з near-api-js v5. `FastAuthSigner` використовує лише `connection.provider.query({request_type:"call_function",...})` і `connection.provider.sendTransaction(...)`.

### Логін

`provider.login()` без аргументів відкриває popup (`Auth0Client.loginWithPopup`). Варіант `login({ redirectUri })` робить redirect. Повертає `{ userId: sub }`, наприклад `google-oauth2|123...`. На сторінці входу тенанта є «Continue with Google», Apple, passkey. Заголовок сторінки «Log in | Example», тобто брендинг спільного клієнта, а не наш.

### Який акаунт отримує користувач

SDK **не створює і не повертає account id**. Він дає лише детермінований ed25519-ключ:

- `provider.getPath()` → `jwt#https://login.testnet.fast-auth.com/#<sub>`;
- `signer.getPublicKey()` → view `v1.signer-prod.testnet::derived_public_key({path, predecessor: "fast-auth.testnet", domain_id: 1})`.

Перевірив живим запитом: view повертає ключ, наприклад `ed25519:FeXV6V...` для тестового `sub`. Акаунт під цей ключ застосунок створює сам: або implicit (`hex(pubkey)`, створюється першим Transfer), або іменований. `signer.createAccount(id)` лише будує `FunctionCall create_account` для реєстратора `testnet`, а надсилає його relayer застосунку (`examples/spa/src/services/fast-auth-relayer.ts`).

### Підпис транзакції (і AddKey)

1. `signer.requestTransactionSignature({ transaction })` робить другий Auth0 popup з `audience = signingAudience`, `scope = "transaction:sign"`, `transaction = borsh(tx)`. Auth0 кладе байти транзакції в claim `fatxn` JWT.
2. `signer.getSignatureRequest()` → `getTokenSilently` → `{ guardId: "jwt#https://login.testnet.fast-auth.com/", verifyPayload: <JWT>, signPayload: fatxn }`.
3. `signer.createSignAction(req, { deposit: 1n })` → `FunctionCall fast-auth.testnet::sign(guard_id, verify_payload, sign_payload, "eddsa")`, 300 Tgas.
4. Цей виклик надсилає **relayer з власного акаунта**. Контракт перевіряє RS256, `iss`, `exp`, `aud == auth0.jwt.fast-auth.testnet` і `fatxn == sign_payload` (`contracts/jwt-guards/auth0-guard/src/lib.rs`). Потім MPC підписує `sha256(sign_payload)` за шляхом `{guard_id}#{sub}` (`contracts/fa/src/lib.rs`). `predecessor` guard ігнорує, тож relayer може бути будь-який.
5. `SuccessValue` = `{"scheme":"Ed25519","signature":[64 байти]}` → `FastAuthSignature.fromBase64(...)` → `signer.sendTransaction(tx, sig)`.

**AddKey з FunctionCall permission підтримується**, бо механізм не залежить від типу дії: підписуються довільні borsh-байти `Transaction`. Окремого прикладу AddKey у docs немає, і як Auth0 показує AddKey на екрані підтвердження, я не перевірив (потрібен справжній вхід через Google).

Живий приклад з testnet: tx `3uNZJyKdQVuZ7JM8BsakykEdZAdANBm4DQ3JZjAZSMzW` (signer `free.deedlords.testnet`, deposit 1 yocto) повернув Ed25519-підпис. Згоріло 38 Tgas, комісія 0.000047 NEAR, депозит повернувся.

## 3. Origin, whitelisting, хто платить

**Callback-и (живий запит `GET /authorize`, response_mode `query` і `web_message`):**

| redirect_uri | результат |
|---|---|
| `http://localhost:3000`, `http://localhost:3000/` | 302 на логін |
| `https://example.fast-auth.com` | 302 |
| `http://localhost:5173` (дефолт Vite), `http://localhost:3001`, `:8080`, `http://localhost`, `https://localhost:3000`, `http://127.0.0.1:3000` | 403 `Callback URL mismatch ... is not in the list of allowed callback URLs` |
| `http://localhost:3000/callback`, `https://example.fast-auth.com/callback` | 403 |
| довільний домен, `*.vercel.app`, `https://auth.near.org` | 403 |

Popup-флоу `auth0-spa-js` бере `redirect_uri = window.location.origin`. Отже застосунок має відкриватися рівно на `http://localhost:3000` (`vite --port 3000 --strictPort`). Preflight на `/oauth/token` відповідає `Access-Control-Allow-Origin: *` для будь-якого origin, але для чужих origin до цього кроку справа не дійде.

Docs кажуть «testnet needs no approval» (https://docs.auth.near.org/resources/testnet). Це правда для контрактів, але не для origin спільного Auth0-клієнта. Whitelisting callback/web origin описано лише в https://docs.auth.near.org/home/apply (поля Callback URL, Web Origin, HTTPS обов'язковий).

**Хто платить:** FastAuth нічого не фінансує. Relayer застосунку платить газ виклику `sign` (≈0.00005 NEAR) і 1 yocto депозиту (повертається). Акаунт користувача має існувати і мати баланс на газ власної транзакції, або треба NEP-366 meta-tx через relayer. Публічного relayer-а немає: `@fast-auth-near/react-sdk` 1.3.1 має захардкоджений `https://localhost:3001/api/relayer/fast-auth` (`dist/providers/fast-auth.provider.js`).

## 4. План інтеграції для Brinewar

### Чому не «додати Google на гостьовий акаунт»

`create_guest` (`contracts/game/src/players.rs`) створює `p-...` з єдиним function-call ключем. Повного ключа немає, тож `AddKey` на `p-...` неможливий ні для кого. Перенести флагман через `mt_transfer` гість теж не може: у `mt_transfer` стоїть `assert_one_yocto`, а function-call ключ депозиту не прикріпить. До того ж `mt_transfer` немає в `GUEST_METHODS`.

### Рекомендований варіант: Google-акаунт як новий дім + `claim_guest` у контракті

Ідея: Google керує implicit-акаунтом `hex(mpcPk)`. Один раз через MPC на нього додається **той самий браузерний ключ гостя** як function-call ключ на `brinewar.testnet`. Далі браузер сам, без popup, викликає `claim_guest()`, і контракт переносить прогрес.

Кроки:

1. **Popup 1 (клік «Save progress with Google»):** `provider.login()` → `signer.getPublicKey()` → `mpcPk`, `accountId = hex(mpcPk.data)`.
2. `POST /api/social/prepare {mpcPublicKey}`: relayer робить `Transfer 0.05 NEAR` на implicit-акаунт (так створюється акаунт з повним ключем `mpcPk`). У відповідь повертає borsh-байти tx: signer = receiver = implicit, `nonce`, `blockHash`, одна дія `AddKey(guestPk, FunctionCall{ allowance 0.25 NEAR, receiver brinewar.testnet, methods GUEST_METHODS + claim_guest })`.
3. **Popup 2 (окрема кнопка «Approve this device»,** бо після асинхронних кроків браузер вже не вважає це жестом і заблокує popup): `Transaction.decode(bytes)` з near-api-js v5 → `signer.requestTransactionSignature({ transaction })` → `signer.getSignatureRequest()` → `POST /api/social/relay {guardId, verifyPayload, signPayload}`.
4. Сервер: декодує `signPayload` і перевіряє, що це рівно очікуваний AddKey на implicit, який він сам готував (receiver, methods, allowance, ключ). Перевіряє, що `derived_public_key(jwt#.../#sub)` збігається з `tx.publicKey`. Далі викликає `fast-auth.testnet::sign` з **1 yocto** і 300 Tgas, перевіряє, що результат не `null`, збирає `SignedTransaction` (near-api-js 7) і надсилає його.
5. Браузер підписує своїм гостьовим ключем, уже як implicit-акаунт: `brinewar.testnet::claim_guest()`. Контракт: `require!(signer_account_id == predecessor_account_id)`, `guest = guest_account_id(&env::signer_account_pk(), parent)`, у гостя немає активної гри, у цілі ще немає профілю гравця. Далі переносить `players`, `balances` (GOLD, флагман, `STARTER_SKIN` і скіни з `skins`), `ShipStats.owner/captain`, `heat_day`, видає NEP-245 події `mt_transfer` і позначає гостя перенесеним. Згода обох сторін доведена в одній tx: ключ гостя є лише в його браузері, а на implicit його додала Google-ідентичність.
6. localStorage: `accountId = implicit`, ключ той самий. Звичайна гра далі без popup.
7. **Новий пристрій:** Google login (popup) → той самий `mpcPk` → акаунт існує → AddKey нового браузерного ключа (popup approve, кроки 2-4 без Transfer) → граємо як implicit. Один раз на пристрій.

Обсяг роботи:

| частина | що | оцінка |
|---|---|---|
| контракт | `claim_guest` + 4-5 тестів (успіх, чужий ключ, активна гра, повторний claim, ціль уже гравець), `claim_guest` у `GUEST_METHODS` для нових гостей, редеплой (стан не змінюється, міграція не потрібна) | 1.5 год |
| сервер | `/api/social/prepare`, `/api/social/relay`, перевірка payload, ліміти з IP і на `sub`, relayer-ключ з env | 1-1.5 год |
| фронт | lazy `import()` модуля з SDK (щоб не роздувати основний бандл), дві кнопки, CSP, `Buffer` polyfill, порт 3000 | 1-1.5 год |
| e2e | ручний прогін з Google на `localhost:3000` | 0.5 год |

### [РІШЕННЯ] для тімейта: relayer з повним ключем

- (а) Тімейт створює `relay.brinewar.testnet` з ~1 NEAR і віддає серверу повний ключ лише від нього. Найменша поверхня атаки: втратити можна до 1 NEAR testnet.
- (б) Використати наявний deployer-ключ `brinewar.testnet` в окремому процесі з одним ендпоінтом. Нічого не треба від тімейта, але повний ключ від контракту опиняється в мережевому процесі. Це суперечить розділу 12 SPEC і runbook (API бачить лише `SPONSOR_*`).
- (в) Проксі в контракті (`relay_sign`, registrar-only, крос-контрактний `sign` з 1 yocto з балансу контракту). Газу вистачає (38 Tgas згоріло з 300), але sponsor-ключ має фіксований список методів, тож тімейт усе одно мусить додати ключ. Плюс більше коду в контракті.

### Дешевший, але нечесний варіант (не рекомендую)

Перевіряти лише `id_token` Google на сервері і тримати мапу `sub → p-...` без on-chain-контролю. На новому пристрої все одно не вийде ходити як `p-...` (ключ не додати), хіба що сервер зберігає приватний ключ гостя. Це кастодіально і суперечить ідеї проєкту.

## 5. Відомі проблеми і CSP

1. **Whitelisting origin** (див. розділ 3). Без нього на нашому домені флоу не працює.
2. **`sign` без депозиту мовчки падає:** tx `bU5RHbDMTQfFXSEbWVTNA71cLLQmBVZ7drmPPavwVWT` (deposit 0) має зовнішній статус success, але `SuccessValue = null`, лог `MPC signing failed`. Завжди 1 yocto і явна перевірка на `null`.
3. **near-api-js v5 поруч з нашим 7.4.0:** провайдер чекає v5 `Transaction` (`encodeTransaction` з `near-api-js/lib/transaction`). Варіант: alias `near-api-js-v5@npm:near-api-js@5.1.1` лише в lazy-модулі. Чи збереться це під Vite 8 / Rollup без проблем з CJS-залежностями (borsh, bn.js), не перевіряв. Запасний шлях: використати `@auth0/auth0-spa-js` напряму. Провайдер робить усього кілька викликів (`loginWithPopup` з `authorizationParams {audience, scope: "transaction:sign", transaction: [...bytes]}` і `getTokenSilently`), байти tx однакові в будь-якій версії.
4. **Глобальний `Buffer`:** SDK використовує його в `viewFunction` і `FastAuthSignature`. Приклад Peersyst ставить `vite-plugin-node-polyfills`.
5. **`react-native-auth0` у залежностях** браузерного пакета: зайве при встановленні, можливі попередження про peer-залежності. Браузерний dist його не імпортує.
6. **Типи:** `dist/index.d.ts` обох пакетів робить `export * from './provider'`, а такого файла в tarball немає. З `skipLibCheck: true` (є в `web/tsconfig.json`) збірка пройде, але частина типів стане `any`.
7. **Popup-блокер:** popup 2 має йти з окремого кліку (див. крок 3).
8. **COOP:** заголовок `Cross-Origin-Opener-Policy: same-origin` зламає `web_message` popup. Підходять `same-origin-allow-popups` або відсутність заголовка. У репозиторії Caddy-конфігу немає, на сервері не перевіряв.
9. **Сторонні cookie:** `getTokenSilently` бере токен з кешу в пам'яті одразу після popup. Перезавантаження сторінки між popup і `getSignatureRequest` призведе до iframe на `login.testnet.fast-auth.com`, який Safari/Firefox ріжуть. Тож не перезавантажуватися і одразу relay-ити, бо JWT має `exp`.
10. **Брендинг:** спільний клієнт показує «Example», а не Brinewar.

CSP (зараз `web/vite.config.ts` збирає meta-CSP з `default-src 'self'`). Для lazy-модуля треба додати:

- `connect-src`: `https://login.testnet.fast-auth.com` (`/oauth/token`, `/userinfo`) плюс наш RPC, бо `derived_public_key` іде через `connection`. Окремих запитів SDK на інші домени не знайшов.
- `frame-src https://login.testnet.fast-auth.com` (silent auth iframe при промаху кешу).
- `script-src`: нічого нового, все бандлиться. Popup є окремим вікном на домені Auth0, наша CSP на нього не діє. Google-вхід відбувається всередині popup.
- `form-action 'self'` не заважає popup-флоу.

## Що не перевірено

- Повний вхід через Google і вигляд екрана підтвердження AddKey (потрібен браузер з Google-акаунтом).
- Чи погодиться Peersyst додати наш origin у спільний testnet-клієнт і як швидко.
- Збірка SDK (near-api-js v5) під Vite 8.
- Чи перевіряє `/oauth/token` Allowed Web Origins окремо від callback (для чужих origin неважливо, бо блок раніше).
- Заголовки COOP на нашому майбутньому домені.
- Privy (запасний варіант (а) з SPEC 6) не досліджував. Там allowed origins налаштовує сам власник App ID, тож блокера whitelisting може не бути.
